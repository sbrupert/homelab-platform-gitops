# Control-plane backups

The normal `control-plane` Flux entrypoint installs two complementary backup tools:

- Velero writes a daily, broad Kubernetes-object archive to Garage. This profile does **not** back up PVC bytes: volume snapshots, snapshot data movement, and filesystem backup are disabled. Use selective restores, not a broad replay of platform controllers.
- `talos-backup` takes an hourly Talos etcd snapshot, encrypts it with age, and uploads it to a separate Garage bucket. This is the primary source for restoring the **same** management cluster after control-plane loss.

See [the backup strategy](../../docs/kubernetes-backup-strategy.md) for the recovery decision tree. The separate `control-plane/recovery` entrypoint intentionally keeps Velero read-only and restore-only; the normal release here uses the same `HelmRelease/velero` identity but enables writes and schedules.

## Prerequisites

1. Enable Talos API access from `kube-system` in the **control-plane Talos machine configuration** (owned by the buildout/Talos provisioning path, not these Flux manifests):

   ```yaml
   machine:
     features:
       kubernetesTalosAPIAccess:
         enabled: true
         allowedRoles:
           - os:etcd:backup
         allowedKubernetesNamespaces:
           - kube-system
   ```

2. Create a dedicated Garage bucket named `talos-etcd-control-plane` with a 10 GiB quota and a key with read/write access to that bucket only. Do not reuse the Velero key. Configure the 14-day `etcd/` lifecycle rule separately, as shown below.
3. Generate an age keypair with `age-keygen -o "$SAFE_KEY_PATH"`, where `SAFE_KEY_PATH` is outside this repository. Get its public recipient with `age-keygen -y "$SAFE_KEY_PATH"`. Store the private identity in 1Password as described below, outside Kubernetes and the Garage-only failure domain. Ensure 1Password remains accessible during a total cluster outage; keep a separately protected recovery copy of the private identity as well.
4. In the `Control Plane` 1Password vault, provide these two items:

   - `talos-etcd-s3-bucket-key-control-plane`: `username` is the Garage access key ID; `password` is its secret access key.
   - `talos-etcd-s3-bucket-age-key-control-plane`: `username` is the public `age1…` recipient; `credential` is the private age identity. Only `username` is synced into Kubernetes by the ExternalSecret. Protect access to `credential` because it can decrypt every backup made for that recipient.

   The Talos ExternalSecret will not become Ready, so its CronJob will not be installed, until all three values resolve.

The existing `velero-s3-bucket-key-control-plane` item and `onepassword-control-plane` ClusterSecretStore remain Velero's credential source.

Garage accepts this S3 lifecycle rule, but the AWS Terraform provider times out after writing it while checking the read-back. Manage it through the S3 API instead of the `aws_s3_bucket_lifecycle_configuration` resource. With Garage credentials configured for the AWS CLI, set and verify the rule from outside the cluster:

```sh
aws --endpoint-url https://s3.infra.int.sbrtech.xyz \
  --region hl1 \
  s3api put-bucket-lifecycle-configuration \
  --bucket talos-etcd-control-plane \
  --lifecycle-configuration \
  '{"Rules":[{"ID":"expire-etcd-snapshots","Status":"Enabled","Filter":{"Prefix":"etcd/"},"Expiration":{"Days":14}}]}'
aws --endpoint-url https://s3.infra.int.sbrtech.xyz \
  --region hl1 \
  s3api get-bucket-lifecycle-configuration \
  --bucket talos-etcd-control-plane
```

The `put` operation replaces **all** lifecycle rules on the bucket; include any additional rules in the same request. At the observed compressed backup size of about 10.69 MB, 14 days of hourly snapshots should use about 3.6 GB, below the 10 GiB quota. Monitor actual bucket usage and backup failures as etcd grows; the quota is a hard limit, not a retention mechanism.

## Reconciliation order

`control-plane/backup.yaml` defines two independent chains:

```text
infrastructure-external-secrets-configs
  ├─ backup-velero-credentials → backup-velero
  └─ backup-talos-etcd-credentials → backup-talos-etcd
```

Each credential Kustomization waits for its ExternalSecret to report `Ready=True`, meaning the target Kubernetes Secret exists. This is stronger than waiting only for the External Secrets controller to start. The Talos job also mounts the Secret generated by its `talos.dev/v1alpha1` ServiceAccount.

## Initial checks

1. Check all four `backup-*` Flux Kustomizations. If the Talos credential one is not Ready, inspect the ExternalSecret and the prerequisite 1Password item; do not substitute a dummy age key.
2. Confirm the normal Velero Deployment does **not** have `--restore-only`, its default BackupStorageLocation is `Available` and `ReadWrite`, and `Schedule/velero-cluster-resources` exists. Inspect a completed scheduled or manual backup's actual resource list; do not infer scope merely from `Completed` status.
3. Trigger a one-off Talos backup Job from `CronJob/talos-backup` in `kube-system`; wait for completion and inspect its logs. Confirm that an encrypted object appears in the dedicated Garage bucket. Download a copy **from outside the cluster**, decrypt it with the private age identity in the 1Password `credential` field (or its separately protected recovery copy), and run a disposable restore drill before treating the schedule as proven.
4. Test the recovery-to-normal Flux path switch separately. The normal Velero Kustomization must adopt the recovery-orphaned HelmRelease and change it to ReadWrite without deleting the installation.

An in-cluster CronJob cannot run after the Kubernetes API/cluster is lost. The snapshot, its decryption key, and the original Talos machine configuration/cluster secrets must all remain accessible without that cluster.
